# 经验与坑（LESSONS）

> 记录 M1 期间真实踩过的坑。每条都尽量落到「现象 → 根因 → 现在的做法 → 对应测试」。
> 后续迭代如果又踩同样的坑，先回来读一遍。

---

## 一、物理：塌落范围最难调

### 坑 1｜打一只，整塔塌

**现象**：一发弹幕命中底部，整座塔连锁塌完。

**根因（三件事叠加，缺一不可）**

1. `topple()` 无条件给**所有**邻居叠加 `0.85 rad/s` 的连锁角速度 → 一传十
2. 判定是"失去 1 个支撑 = 不稳"→ 每层影响数翻倍：2 → 4 → 8 → 14（整圈）
3. 倾角永不回正 → 每次微小扰动都累积

**现在的做法**：支撑判定只在"失去全部支撑"时触发；横向连锁只推**顺方向的一只**、
且只加 0.02 rad 倾角（永远不会触发翻倒判定）；倾角不再回正，谁倒由
「每次命中叠加随机倾角（3 候选值）→ 满 10 次或超 0.42 rad」决定。

**教训**：连锁参数必须小于翻倒阈值，否则"扰动"会自己长成雪崩。

---

### 坑 2｜"倒三角"也能撑住（悬挑）

**现象**：缺口上方一排杯子悬在空气里，像倒三角一样立着。

**根因**：判据写成了"**至少还有一个支撑**就站住"。砖缝错位下，每只杯有两个支撑，
丢一个还剩一个（单点接触），于是任何缺口上方都能靠单点悬挑续命。

**现在的做法**：

```ts
// 必须两只支撑都在（完全嵌在下层杯缝里）
const supporting = cup.supporters.every((id) => isAlive(world.byId.get(id)))
```

**教训**：真实纸杯**没有粘接**，单点接触 = 悬挑 = 必然滑落。判据要按"支撑多边形"想，而不是"有没有支撑"。

---

### 坑 3｜用"环向完整性"补塌落范围 → 整圈同时消失

**现象**：一层掉了过半，剩下半圈被一次性推倒，看起来"上方一整圈瞬间没了"。

**根因**：我为了放大"上方塌更多"，加了一条 `hoopIntegrity=0.5`：一层存活率低于 50% 就判整层失稳。
但现实里剩下的杯弧照样能立在桌面上，这条规则不符合现实。

**现在的做法**：`hoopIntegrity: 1`（默认关闭），代码路径保留但不再参与。
塌落范围只由"支撑丢失"决定，结果自然是**缺口正上方楔形收窄**。

**测试**：`局部缺口不会把剩下的半圈一起清掉`、`只有支撑全没了才会塌，塌的范围不超过"上方楔形"`。

---

### 坑 4｜为了"结构正确"改成竖直对齐 → 不像叠杯塔了

**现象**：把每层改为与下层完全对齐（1:1 垂直支撑）后，视觉变成"格子墙"，
用户一眼看出"这不是叠杯塔"。

**根因**：叠杯塔的形态特征就是**砖缝错位**——每只杯压在下面两只杯之间的缝里。
竖直对齐让结构判定变简单（不会悬挑），但丢掉了产品识别度。

**现在的做法**：保留砖缝（奇数层错半格），用"必须两只支撑都在"来消灭悬挑。
**视觉特征不能为了结构简单而牺牲。**

---

### 坑 5｜杯子看起来"分开站着"

**现象**：放大看，杯与杯之间有明显缝隙，不像挤在一起的杯墙。

**根因**：几何参数没算密度。半径 118、每层 24 只 → 间距 30.9px，而杯宽只有 27px → 缝 3.9px。

**现在的做法**：每层 27 只 + 杯宽 28 → 间距 ≈ 杯宽，视觉贴合。
**教训**：环状排布的密度要按 `2πR / n ≈ cupW` 反推数量，而不是先定数量。

---

### 坑 6｜小测试塔会"绕环一周"，导致假失败

**现象**：断言"任何一层都不能被整圈清空"在每层 8 只的测试塔上失败。

**根因**：8 只环周长太短，3 只的缺口向上扩散时很容易绕回起点，看起来像整圈塌。

**现在的做法**：结构类测试用"每层 20 只 × 6 层"，或者断言"缺口是局部"而不是精确数量。
**教训**：物理测试的场地尺寸必须接近真实比例，否则测的是拓扑，不是行为。

## 二、动画：观感问题往往来自状态机，不是渲染

### 坑 7｜翻倒动画"弹回直立再倒一次"

**现象**：杯子先被推歪，然后突然回正，再重新倒下去。

**根因**：`toppledTilt` 从 `0` 起算。杯子进入翻倒状态时倾角本来是 0.34 rad，
动画却从 0 开始 → 视觉上先归零。

**现在的做法**：`topple()` 记录 `fallFrom = cup.tilt`，动画从当前倾角插值到 ±90°。

**测试**：`翻倒动画从当前倾角接着倒，不会弹回直立再跌一次`（首帧角度、单调性、单帧无跳变）。

---

### 坑 8｜"一瞬间全倒"，没有多米诺

**现象**：一次命中，整片杯子在同一帧同时开始倒。

**根因**：`relaxStructure` 直接对整批杯子调用 `topple()`。

**现在的做法**：结构失效只**排队**（`pendingMs = 110 + jitter`），到点才翻倒。
排队中的杯子仍算"活着"→ 上层必须等它真倒了才失去支撑，于是塌落按层传递。

**测试**：`支撑杯被拿掉 → 同列上方按层排队倒塌（不是同一帧齐倒）`、`排队延时错峰`。

---

### 坑 9｜倒地后"一碰就没"

**现象**：杯子倒到 90° 的那一帧直接消失，像被删除而不是倒下。

**现在的做法**：`settleHoldMs=320` 停留 + 渐隐（`cupAlpha` 按 `lieMs` 淡出）；
缓动从 `ease-out` 换成 `smoothstep`（慢起—加速—落地）；侧滑位移 12px → 16px。

---

### 坑 17｜杯口从前面杯体里"漏"出来，杯口反盖杯底

**现象**：远近杯子重叠处，后面杯子的白色杯口会透到前面杯子身上；有时下层杯的杯口
还会压在上层杯的杯底之上，透视完全反了。

**根因（两处叠加）**

1. 杯子按深度做了 alpha：`alpha = 0.55 + 0.45 * depth` → 前杯只有 0.55–1.0 不透明，
   后面的白色杯口自然透出来；
2. 排序只按 `depth`，但砖缝错位会给相邻层带来约 0.007 的深度差——
   上层杯的深度可能略小于下层杯，于是上层被**先画**、下层杯口**后画**，
   视觉上就变成"杯口盖住杯底"。

**现在的做法**：

```ts
// 1. 完全不通明，纵深改用 tint 调暗
const lit = 0.72 + 0.28 * ((depth + 1) / 2)
g.tint = gray(lit)
// 2. 排序加层高偏置，让上层杯底稳定压住下层杯口
sort((a, b) => (a.depth + a.layer * 0.004) - (b.depth + b.layer * 0.004))
```

`0.004 × 12 层 = 0.048`：足够盖过砖缝的 0.007 深度抖动，又不会打乱整圈前后关系。

**教训**：伪 3D 里"谁遮挡谁"不能只靠一个深度标量；**同一物体内部的接触关系**
（上层压下层）要靠层序偏置表达。透明度也不能用来表达纵深——它会让遮挡失效。

---

### 坑 18｜命中造成的翻倒不触发结构重算

**现象**：一发火箭把底层整圈打掉，上方却纹丝不动，要等下一次别的原因产生翻倒才开始塌。

**根因**：`toppledThisFrame` 在"弹体命中结算"**之后**才清零，于是命中阶段产生的翻倒
把计数器加到 1，紧接着被清零，`if (toppledThisFrame > 0) relaxStructure()` 永远为假。

**现在的做法**：计数器在 `advance()` 最开头清零，命中与结构塌落共用同一帧计数。

**测试**：`火箭彩虹清杯：整圈底层被打掉 → 大面积塌落`（修之前只塌了底层 22 只，
修之后整个塔连锁倒塌）。

**教训**：同一帧内"谁产生了事件 / 谁消费了事件"的计数，必须在帧首清零。
这类 bug 不会报错，只会让某个分支静默失效。

## 三、命中：弹体穿模

### 坑 10｜弹幕怎么打都打不倒杯子

**现象**：连按空格几十次，几乎不产生命中。

**根因**：`Session.autoTimer` 用 `setInterval(…, 100ms)` 推进 → 每步 100px，
而碰撞半径 18px → 单步直接跨过目标，命中率约 18%。**这是穿模，不是概率**。

**现在的做法**：

- 时间轴交给 Pixi ticker（约 16ms/帧）
- 碰撞改为**扫掠检测**（线段—圆相交，半径 20），任何步长都不会跨过
- 回归测试覆盖 100ms 粗步长

**教训**：任何"移动 + 碰撞"的系统，先问一句"最大单步位移 vs 碰撞体尺寸"。
另外不要用定时器驱动物理，用渲染帧。

---

### 坑 11｜弹体刚出生就被判死

**现象**：弹体不出现 / 命中率异常低。

**根因**：炮口在 `y = baseY + 184`（约 780），而销毁条件是 `y > 720`，弹体出生即消失。

**现在的做法**：销毁阈值改到 `y > 900`，并且只按 `age` 或出屏判断。

## 四、工程与环境

### 坑 12｜pnpm 11 的 `allowBuilds` 放错文件

- `allowBuilds` 必须写在 **`pnpm-workspace.yaml`**，写进 `.npmrc` 不生效，报 `ERR_PNPM_IGNORED_BUILDS`
- `.npmrc` 里 `ignore-scripts=true` + `node-linker=hoisted`：后者解决 `Cannot find package '@vitest/utils'`
- registry 超时 → 换 `registry.npmmirror.com`

### 坑 13｜沙箱里跑不起来 vite / vitest

esbuild 需要子进程 spawn，受沙箱限制会失败；构建还需要可写的 `TEMP/TMP`。
做法：把 `TEMP`/`TMP` 指到工作区 `.tmp`，并在需要时用更高权限执行构建与测试。

### 坑 14｜单文件打包出现重复 `<script>`

`build-single.mjs` 会先**清掉所有**外部 script 标签，再注入**唯一一份**内联 bundle，
最后做一次自检：挖空内联内容后，HTML 壳里不允许再残留任何 `src`/`href`。

---

### 坑 19｜测试塔配置漏了 `outerRadius`，选靶被吸到圆心

**现象**：爱心 5 发（应为 10 次叠加）打不倒任何杯子；调试发现命中被拆成 2 + 8，
后 8 次全打到 id 60 那只"外圈"杯上。

**根因**：测试配置写了 `outerLayers: 2, outerCount: 12`，却没给 `outerRadius`（默认 0），
于是外圈杯子全被建在**转盘轴心上**：`depth` 恒为 1、`x` 恒为 640，看起来永远在正前方，
把真正的目标顶掉了。

**现在的做法**：

- 小测试塔不再启用外圈（生产配置本身就是 `outerLayers: 0`）
- `pickTarget` 增加防护：`cup.radius <= 0` 的退化杯不参与选靶

**教训**：可选几何参数一定要有"关闭态"的默认值，并且**退化值要显式拒绝**，
否则配置写漏不会报错，只会变成"看起来能打中、其实打错对象"。

## 五、协作与产品

### 坑 15｜看不见画面时盲改物理规则

**现象**：连续几轮"调物理"，结果越改越偏（结构对但形态不对）。

**根因**：只靠文字描述推测画面，每次都同时改多个维度（结构 + 动画 + 密度），
无法判断是哪一处出错。

**现在的做法**：

- 一次只改一个维度，改完必须能看到画面
- 让用户提供**截图**，并明确指认"哪一处不对"（排布 / 密度 / 比例 / 杯型）
- 形态类问题（像不像叠杯塔）优先级高于物理参数

### 坑 16｜合规红线是硬约束，不是文案问题

资金单向、无阵营、无输赢、礼物只加量、禁用词 —— 全在 [compliance.md](compliance.md)。
**每次加功能先过一遍红线表**，比事后改便宜得多。

## 附：调试经验

- 物理问题先在 **Vitest 里复现**，不要在浏览器里试；确定性步进比肉眼快得多
- 断言**行为**（"不会整圈清空"、"角度单调"），不要断言实现细节（toppled 还是 fallen）
- 一次 `stepAll(…, 40)` 就是 640ms，比真实等待快 10 倍
- 数值回归：任何物理参数改动都跑一遍全套测试，48 条用例大约 0.3s
